# 週次更新の正本

対象はこのリポジトリだけ。週 1 回、土曜 08:00 頃（Asia/Tokyo）に 1 つの必須の仕掛けを追加する。日付は予定日の JST 日付。初回は `2026-10-03`。準備日が前日でもこの日付を使い、同じ週を二度生成しない。リポジトリ内に scheduler や常駐プロセスを設けない。

## 再開前の読込み

1. 最新 main と `docs/DESIGN.md`、この文書を読む
2. `pipeline.json` と `docs/runs/<week>.json` の完成記録を照合する
3. 当週が完成済みなら結果を検証して終了。新しい仕掛けを増やさない
4. 未完成の同週ブランチがある場合はその状態を調べて修復する。停止した週をまとめて取り戻さない

次の予定: 第 2 週は議案提出の独自言語。辞書生成→翻訳→逆翻訳の検査結果を既存の文字議会が必ず消費する。第 3 週は翻訳と議決の履歴証明を別検証器で確認する。次週の仕掛けだけを実装し、先の仕掛けを同時追加しない。

## 更新手順

1. repo 単位で排他を確保する。ローカル作業には `flock -n "$(git rev-parse --git-common-dir)/hello-world-update.lock"` を使用できる。同時に動く別クラウド作業の有無も確認する。ローカル flock だけで別マシンを排他できると扱わない。排他・停止指示の状況が不明なら公開を止める
2. main の起点 SHA を取得・記録し、同週作業ブランチで作業する
3. 新しい週モジュールと、その必須成果物を後段が消費する経路を 1 つ追加する。`pipeline.json` の登録を更新し、旧工程を残す。固定入力・固定 seed を保つ
4. 正常出力、再現性、新成果物の欠落・変更、順序違い、symlink/path、重複週、競合、停止、排他、資源制限をテストする。先に失敗を確認し、実装後に成功させる
5. 実行前に差分・追加依存・テスト用の負荷処理をレビューする。任意コードやネット接続を扱う runner に拡張しない
6. `python3 -B -m unittest discover -s tests -v` と README の空の作業領域からの実行を検証。各実行の 10 秒・プロセス別予算を守る。前週完成版の回帰試験を実行する（第 1 週には前週なし）
7. `docs/runs/<week>.json` に元 SHA、版、環境、コマンド、終了コード、出力照合、所要時間、資源検証、レビュー結果を記録する。未実施は未実施とする
8. 公開直前に最新 remote SHA を取り直す。起点と異なる、停止が入った、試験失敗、レビュー未完了なら公開しない。`hello_world.release.publication_allowed` はこの判定の純粋関数。ネット通信や実際の公開は行わない
9. `force` なしの通常 fast-forward で更新する。更新中に競合した場合は停止。ユーザー編集を上書きしない
10. remote が公開 commit に一致することを確認する。既存 CI がある場合はその SHA の結果も確認し、追加内容と検証結果を報告する

## 再開時の実行入口

- 製品: `python3 -B -m hello_world.cli run --run-id <fresh-id>`
- プロセス制限確認: `python3 -B -m hello_world.cli limits --run-id <fresh-id>`
- 回帰: `python3 -B -m unittest discover -s tests -v`
- 順序・依存: `pipeline.json`
- 安全条件: `docs/DESIGN.md` と `hello_world/limits.json`
- 完成記録: `docs/runs/<scheduled-JST-date>.json`

新しい認証・課金・権限・規約同意や上限拡大が必要なら、先に確認する。外部依存は不可欠な場合だけ、固定版・入手元・ライセンス・理由を記録する。repo のライセンスは追加・変更しない。公開内容は作品の仕様と操作情報のみ。会話、秘密、個人情報を含めない。
